# データ取り扱いルール

扱うのは**ユーザーが撮った写真**。部屋の中・顔・手書きの文字・位置が写りうる。以下は実装後に足す対策ではなく、書き始める前の制約として扱う。

## 写真

- **ディスクに書かない。** メモリ上で AI に渡し、応答を返したら捨てる。一時ファイル・アップロードディレクトリ・キャッシュを作らない。`UploadFile` は `await file.read()` でメモリに読み、`tempfile` や `SpooledTemporaryFile` のディスク退避に頼らない。本文の上限 1 MB (契約) を先に確かめ、Starlette が multipart を一時ファイルに退避しない大きさに収める。
- **ログに出さない。** 画像のバイト列、AI の生の出力 (写真の説明文)、EXIF をログ・例外の文・トレースに入れない。記録してよいのは、例外の型・経路・状態コード・所要時間・トークン数だけ。
- **応答に入れない。** 応答は契約 (`api/openapi.yaml`) の項目だけ。AI の生の説明文や画像を返さない。エラーの応答にも入力の中身を入れない。
- **AI にはインラインで送る。** Files API・context caching・検索のグラウンディングなど、提供元に写真が別に残る機能を使わない (project-penguin #125)。

## 端末とユーザー

- 端末やユーザーを特定できる値 (端末の ID・IP の保存・広告 ID) を受け取らない・残さない。
- みんなの氷山 (DynamoDB、project-penguin の ADR 0002) に保存するのは、件数と、提出の記録 (判定の `Idempotency-Key` と TTL だけ) にする。`Idempotency-Key` は写真ごとの乱数で、誰が送ったかは残らない。写真から作った値 (ハッシュなど) は記録しない。
- 判定の `activity` (移動の分数の要約) は判定の裏付けにだけ使い、保存もログへの記録もしない。

## すれ違い

- トークンは端末が作る 16 バイトの乱数で、クライアントはアプリの 1 日ごとに作り直す。端末の ID・広告 ID から作らない。
- 位置を受け取らない・残さない。サーバーに残すのは、2 つのトークンの組と報告したトークンの集合 (`enc#`)、トークンごとの報告の数 (`encrate#`) だけで、どちらも 2 日で消える (TTL)。
- トークンをログ・例外の文に出さない。

## API キー

- 環境変数からのみ読む (`Settings`、名前は `PENGUIN_` で始める)。コード・設定ファイル・テストのフィクスチャ・`.env.example` に実値を書かない。
- **Unity クライアントに一切渡さない。** ビルドを展開すれば取り出せるため。

## テストデータ

- **実在の人や部屋が写った写真をリポジトリに置かない。** テストは合成画像か、AI をモックにして画像を使わない形にする。評価用の写真セット (project-penguin #89) はリポジトリの外に置く。

## 認証

エンドポイントの認証は無い (Hack Day の範囲)。クライアントに固定のシークレットを埋めるのは対策にならないので、そういう「API キーのヘッダー」を実装しない。乱用はレート制限 (`rate_limited`) と AI 側の上限額で抑える。
