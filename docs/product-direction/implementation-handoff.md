## 依頼する作業

新しい工場ゲームの仕様に沿って、未実装の機能を確認し、実装・画面への接続・検証まで進める。主な対象は本リポジトリの `unity/`。旧 Web 版は凍結済みであり、新規機能の実装先にしない。

最初に `CLAUDE.md` と `AGENTS.md` を読み、`sh scripts/setup_hooks.sh` を実行する。作業ブランチを用意し、既存の未コミット変更を確認する。実装計画には、対象機能・参照仕様・変更するコード・検証方法を記載する。

この文書は新しいゲームルールの決定書ではない。以下の「確定仕様」「既に記載されている検討値」「本当に未決の事項」を区別し、検討値を製品の確定値として扱わない。未決事項に依存しない実装は進め、必要な判断だけを具体的に確認する。

## 守るゲームの方針

- 日常の入力は歩数→ガス、24時間からスクリーンタイムを引いた時間→電気、水の記録→水。入力の取得・換算と、工場での消費を分ける。
- 水の元の確定方針はバーコードをスキャンした時点の付与。現行試作と backend は写真記録の経路を持つ。この差を確認し、写真方式への置換や両方式からの二重付与を暗黙に決めない。
- 電気の今回の試作は前日のスクリーンタイム画像を使う方針。合成入力を実測・実取得として見せない。運用時の Family Controls は別の検証項目とする。
- 現実由来のエネルギーを、工場内で無料かつ無限に再生産するループを作らない。既存試作のガス日次上限なしという挙動を、理由なく変更しない。
- 横並びの施設で資源を受け渡し、遠方には施設の連なりか倉庫を使う。倉庫が配送を自動調整し、施設は自分が使わない資源も中継できる。上位資源を下位施設の材料には使わない。
- すべてのズーム段階で直前の段階の2×2を上位の1グリッドにまとめる。1ズームを基準に2ズームは4個分、3ズームは16個分。MVPでは初期から1・2ズームを利用でき、納品でランクを上げると3ズームを解放できる。
- ズームアウトでレイアウトと当たり判定を上位施設へ完全に切り替え、その施設のエフォートとコンボを確認できるようにする。ズームインで下位施設の確認・編集へ戻る。内部と上位の生産を両方行う方針を保ち、往復だけで在庫や納品実績を変えない。
- 納品はランク上げのために行う。週ノルマ・超過報酬を復活させない。加工で使った品物を納品でも数えない。
- ペンギンは種類の解放と個体の獲得を分ける。解放だけで個体を付与せず、すれ違いで獲得する。所持効果とし、配属操作を製品の前提にしない。
- エフォートとコンボは併用する。ガス・電気の供給比率や日ごとの変化によって、投資の比重・順番・進捗が変わることを検証する。

## 既に記載されている数値と構成

次の値は既存の検討案であり、新しく推測する必要はない。採用状況を確認し、試作用に使う場合は、変更できるデータとして扱い、画面や説明でも試作値と区別する。

- 資源はR0〜R4、施設はF0〜F4、ズーム階層Z、生産レベルLvを別々に扱う。
- 現行モデルは主材料の必要量100→1,000→10,000、Lv1出力100、Lv倍率1・3・10・30・100。
- 漁場・海藻場・製塩所・さばき場・干物場・かまぼこ・ちくわ・ギフト・研究所・おでんの材料、時間、追加エネルギーは、施設案と `progression-model.json` にある。
- 全次数の生産品を直接納品する案と品目別の納品点がある。魚1、すり身4、おでん300など。城のレベル閾値が存在するという意味ではない。
- 2×2のおでん工房は、かまぼこ・ちくわ・海藻場・倉庫。ギフトは漁場・製塩所・干物場・倉庫。研究所は漁場・さばき場・海藻場・倉庫の候補が記載済み。
- ペンギン19種の対象資源・ID・重み・解放段階案は記載済み。全解放時の重み合計は10,000、S1は6,000、S2は8,600、S3は9,900。
- 所持効果は `基礎量 × (1 + 加算率合計) × (1 + 倍率枠の率合計)`。同種の率は羽数分を加え、指数的に掛けない。小数は資源ごとに繰り越す。
- 新種保証案は20回連続で新種なしなら次の21回目に解放済み・未所持だけから重み抽選。日をまたいで保持し、対象外の再遭遇では進めない。
- 同じ相手の報酬はゲーム内1日1回、合計1日10羽は試作用の案。現行コードの03:00 JSTの日付切替と、記録画像の00:00 JSTの対象日を混同しない。

## 実装する順番と受け入れ条件

### 1. 現状の照合と保存・再開

最新コードを読み、上の一覧を「実装済み・未接続・未実装・仕様待ち」に分ける。既存テストを先に実行し、比較基準を残す。

新しい工場の保存は、エネルギー残高、歩数の受領済み最大値、水・電気の受領台帳、配置、施設別在庫、配送・加工の予約と時刻、ペンギン所持・解放、新種保証、すれ違いの日次状態を一つの版付き状態として扱う。画像やAIの生出力は含めない。

候補状態を保存できてから付与や支出を公開する。保存失敗・強制終了・壊れた保存・新しい版の保存を扱い、同じ歩数や記録、すれ違いの再報告で二重付与されないことをテストする。すれ違いの成立記録だけ保存して個体を失う、または個体だけ保存して再度獲得する状態を作らない。

中断中も生産するか、オフライン精算の上限は未決。永続化の実装に合わせて、勝手にオフライン報酬を追加しない。

### 2. 生産・配置・物流・納品

既存アセットを活かして、生産型と加工型、品目別在庫、必要材料とエネルギー、開始と完了を持つ生産を画面につなぐ。合成原料4個だけを処理して終わる比較試作を、完成した工場ゲームとは扱わない。

支払済みの加工・配送は燃料不足になっても完了し、未開始分は在庫を保持して待機する。受取容量を予約し、満杯への過剰配送、消失、複製、経路の往復による増殖を防ぐ。停止理由を表示する。

納品は在庫消費と評価を同時に確定する。同じ操作の再送・再開で重複計上しない。城の閾値などが未決でも、品目・数量を検証して納品する処理は独立して実装できる。

### 3. 組み合わせ・拡張・投資

[ズーム仕様の受け入れ条件](zoom-out.md#実装時に確認すること)を満たす。各段階で直前の段階の2×2を上位の1グリッドへ対応させ、段階ごとにレイアウト・当たり判定・施設選択とエフォート・コンボの確認対象を切り替える。各段階の構成候補と既存のパターン検出を照合し、確認された成立・稼働条件に沿って実装する。ズーム表示の切替で生産状態を作り直さず、内部と上位の材料・エネルギーを二重に消費しない。編集中の在庫・加工途中・配送予約の扱いを先に定義して検証する。

土地拡張、施設建設、エフォート、コンボを画面から操作できるようにする。費用・倍率・対象範囲の未決部分は、既存仕様を探したうえで、決める必要がある項目を絞って確認する。

### 4. ペンギンと日常入力

19種のデータ、解放と所持、加算と倍率、新種保証を扱う。増量はR0付与時または生産完了時の1回のみ適用し、中継・倉庫・納品・再開では再適用しない。解放するだけで個体が増えないこと、抽選候補に未解放が入らないことを検証する。

実際の日常入力を接続し、権限なし・対象日不一致・取消・タイムアウト・通信失敗を表示する。水の取得方法の食い違いを解消してから付与経路を確定する。iOSのすれ違いは2台で確認し、前面での動作とバックグラウンドでの動作を分けて報告する。

## 本当に未決の事項

既存資料には次の最終ルールが記載されていない。まず最新資料やコードで再確認し、なお不明なときだけ、参照箇所・選択肢・影響を示して確認する。

- ランクごとの納品条件と3ズームを解放する必要ランク、ペンギンの種類の解放条件。初期1・2ズームとMVPの到達目標3ズームは確定済み。
- 各段階の2×2区画の原点・境界・重複範囲、並び順・向き・接続の成立条件、上位生産の開始時点、編集で崩したときの未完了処理。
- 内部・上位・外部配送の消費優先順位と、自動配送の配分基準。
- 土地拡張が対象とする階層、隣接条件、費用、上限。
- エフォートの追加ガス消費と増産量、コンボの範囲と倍率、両者の合成式、建設費の増加式。上位施設の設定の持ち方・変更操作と階層間での効果の重ね方。
- 水と電気の本番換算率、同一商品の回数制限、画像の読取方法と訂正の扱い。
- オフライン生産、再開時の経過時間上限、初期支給、既存セーブの移行。

仕様が決まっていない部分だけを理由に、他の機能まで保留しない。実装の都合で新しい制約を足した場合は、製品仕様の確定と区別して記録する。

## 検証と完了報告

Domainのテストでは、資源不足、容量予約、途中停止、時間分割、二重受領、保存失敗と復旧、日付変更、桁が大きい数量、増量の端数を確認する。ズームの往復と再起動によって在庫・進行が変わらないことも確認する。

専用シーンで「日常入力→受領→建設・配置→自動配送と加工→納品→成長」を操作して確認する。開発用の入力、未接続の機能、実機で未確認の範囲を画面と報告で区別する。描画負荷と生産計算の負荷は別々に測り、未測定の性能改善を達成済みとしない。

通信を追加・変更するときは、コードより先に `api/openapi.yaml` と `api/examples/` を更新する。AIとAWSはテストでは偽物を使う。写真とAIの生出力をディスク・ログ・応答に残さず、キーは環境変数だけから読む。

変更後は `.claude/skills/verify/SKILL.md` の検査と、影響するUnityテストを実行する。Unityの新規アセットには `.meta` を含める。実機が必要な項目は、実行環境と結果を記録し、未実施を成功として扱わない。

最後に、追加した機能、変更ファイル、検証結果、未解決事項、起動して確認する手順を報告する。人の名前・連絡先・個人の事情・会話の引用は記録しない。commit・push・PRは、それぞれ指示された範囲でのみ行う。
