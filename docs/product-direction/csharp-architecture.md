# 物流ゲームのC#構造

更新日: 2026-10-24。Unityクライアントの実装方針を整理した参考資料。具体的なクラス名は役割の例であり、backendにUnityコードを追加する計画ではない。

## 責務の分離

```text
入力・時計・歩数
    ↓
Session / Driver
    ↓ 操作と時刻
Facade → 内部状態とルール処理
    ↓
Result / Event / View
    ↓
Presenter → 3D・RectTransform・UI
```

| 要素 | 担当すること | 担当しないこと |
|---|---|---|
| State | 施設、在庫、配送中の荷物、加工進捗、燃料、受領済み台帳 | 描画、OSの権限、通信 |
| Facade | 操作の公開入口、操作の可否、時間進行 | UI部品の制御 |
| Flow / Service | 出荷、到着、容量予約、材料消費、加工完了 | 演出の完了待ち |
| View | 表示に必要な現在状態の写し | 内部状態を直接変更する経路 |
| Result | 成功・失敗と理由 | 表示側でのルール再判定 |
| Event | 出荷・到着・加工完了などの出来事 | 在庫を増減するコールバック |
| Session / Driver | 時計・歩数・入力・保存の順序、起動と中断復帰 | 生産量や配送費の計算 |
| Presenter | モデル、線、荷物、進捗、数量の表示 | 資源の消費・付与 |
| Store | 版付きデータの保存・復元 | ゲームの進行判断 |

## 状態と時間

ゲーム計算はUnityEngineに依存しないC#で実装する。時刻を外から渡し、内部で端末の現在時刻を読まない。複数の施設は並行して進め、演出待ちで工場全体を止めない。

配送中の荷物は、品目、数量、送り元、送り先、出発時刻、到着時刻を持つ。表示側は時刻から位置を求める。アニメーションが完了したことを理由に在庫を加えない。

出荷時は燃料・在庫・容量予約・荷物を同時に更新する。加工開始時は材料と燃料を一度だけ消費する。支払済みの作業と未開始の作業を区別する。

同じ時刻に到着・加工完了・入力が重なる順番を明示する。同期間をまとめて進める場合と分けて進める場合で結果が一致することをテストする。

## 保存と歩数

ガス残高、付与台帳、配送・加工の進捗は同じ保存単位へ含める。歩数は日ごとの累計最大値と付与済み量を用いて差分だけ付与する。再問い合わせや再起動で同じ歩数を二重に換算しない。

UTC時刻との対応はSessionが管理し、Domainは論理時刻を持つ。時計が戻っても保存済みの時刻基準を後退させない。復帰時に新しく受け取ったガスを過去の生産に投入しない。

Viewと保存データは用途を分ける。表示用の配列や辞書は内部状態の可変参照を漏らさないようコピーする。読み取り専用の宣言だけで深い不変性が保証されるとは考えない。

## 実装時の確認

変更前に呼び出し元・呼び出し先・生成箇所を一段ずつ確認する。既存のクラス数や名称を模倣するために分割せず、一つのクラスに計算・保存・表示が混ざっていないかを見る。

完了報告には、変更ファイル、コードを読む順番、責務を分けた理由と依存の向き、実行した検証と未確認事項を記載する。iOS実機で確認していない項目を完了扱いにしない。
