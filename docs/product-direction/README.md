# 日常の行動で動かす iOS 工場ゲーム

更新日: 2026-10-26。製品の新しい方向性をまとめた設計文書。実装済みの仕様を表すものではない。

歩行による燃料補給と工場の効率化を比較する[歩行と効率化の設計案](walking-health-concept.md)、[C#構造](csharp-architecture.md)、[実装計画](walking-implementation-plan.md)を補足資料として追加した。補足資料の仮値や比較方法は、以下の確定事項を置き換えない。

**日常で集めたエネルギーを使って工場をつなぎ、建物の組み合わせを階層的に育てていく iOS ゲーム。** 主役となる遊びは、建物の配置を工夫し、ズームアウト先の上位施設で新しい資源を生む「組み合わせ」である。納品でランクを上げ、ズーム段階を解放することを目標とする。

この方針で従来の製品方針を置き換える。写真による資源獲得・従来の共有在庫方式・記録や実績によるペンギン獲得は、そのまま前提にしない。氷の減少、港の注文、お魚の通貨などの旧機能は個別に見直す。既存の API 契約・コード・公開手順はこの文書だけでは変更されない。

「確定」は製品方針として確認された内容、「仮説・提案」は今後検証する内容、「未決」は回答が必要な内容を意味する。換算率や建物の具体例は、明記がない限り確定値ではない。

## 確定: 現実のロジック

| 現実での入力 | ゲーム内で増えるもの | 現時点のルール | 未決の詳細 |
|---|---|---|---|
| 歩数 | ガスエネルギー | 歩いた量をエネルギーへ換算する | 換算率、日次上限、歩数の集計元 |
| スクリーンタイム | 電気エネルギー | 1日の24時間からスクリーンタイムを引いた時間に応じて得る | 対象端末・アプリ、受取時刻、換算率、OS上の取得方法 |
| 飲んだ水 | 水エネルギー | 飲みきった空のペットボトルを撮り、AI がラベルの容量と残りを見積もった飲んだ量で付与する (2026-10-25 にバーコードから変更) | 換算率と 1 日の上限 (試作値は 150ml ごとに 1・1 日 3,000ml)、マイボトル対応 |
| 他の利用者とのすれ違い | ペンギンの数と種類 | 解放した種類のペンギンをすれ違いで獲得する | 検知方式、同じ相手との再遭遇、獲得する種類の決定方法 |

電気の換算元は `非使用時間 = 24時間 − その日のスクリーンタイム`。電気への換算係数は未決。日次確定時に付与するか、日中の経過時間で仮計算するかも未決で、朝の時点で24時間分を繰り返し受け取れる設計にはしない。

現実の入力を集計・換算する責務と、工場がエネルギーを使う責務を分ける。受取済みの集計を再取得しても、同じ行動から二重に資源を得ない設計が必要。権限を与えない場合、取得できない場合、初日の資源をどうするかは確認事項とする。

### 水の受け取りと回数制限

水エネルギーはスキャン時に付与する。スキャンは水を実際に飲んだ量の測定ではないため、記録した量と実測した量を区別する。1回の付与量を商品容量に応じて変えるかは未決。

同じ商品の繰り返し読み取りを抑えるため、**同一商品は1日に1回まで付与する案**がある。まだ確定した制限ではない。同じ商品コードの商品を実際に2本飲んだ場合も、2本目は対象外になる。別の商品なら繰り返し受け取れるため、この制限だけでは1日の総量は抑えられない。

試作では、同一商品コードの1日1回制限を候補とする。付与量、1日の総量上限、日付を切り替える基準、マイボトルや水道水の扱いは別途決める。

## 確定: ゲームのロジック

- 工場は現実で得たエネルギーを消費し、別の資源を生産する。
- 横並びの施設間で資源をやり取りする。施設間に線を手動で引く方式を基本にしない。
- 離れた場所へ資源を送るには、途中まで施設を連ねるか、倉庫を介して運ぶ。
- 倉庫は複雑な物流の調整を自動で行う施設とする。利用者が細かな配送設定を行うことは基本にしない。自動調整の範囲と判断基準は未決。
- 施設は、自分が生産に使わない鉄などの資源も中継できる。
- 上位の資源は下位施設では材料として使わず、通過させる。
- 工場には、材料を別のものに加工する「加工型」と、資源を生み出す「生産型」がある。生産型もエネルギーを使う。
- 納品によってランクを上げるほど、利用できるズーム段階が増える。MVPでは初期から1ズーム・2ズームを利用でき、ランク上昇によって3ズームを解放できる。MVPの仮設定はランク2・すり身と干物の累計納品5個。
- どのズーム段階でも、直前の段階の2×2グリッドを上位の1グリッドにまとめる。1ズームを基準に、2ズームは2×2の4個分、3ズームは4×4の16個分になる。
- ズームアウトすると、レイアウトと当たり判定をその段階の上位施設へ完全に切り替える。エフォートとコンボも、その上位施設を対象に確認できる。
- 土地の拡張は2×2マスを1区画として行う。
- 生産した品物の使い道は、当面ランク上げのための納品のみとする。週の納品量ノルマは設けない。
- ペンギンは種類を解放した後、すれ違いで獲得する。種類の解放条件は未決。
- ズームインすれば下位のレイアウトと当たり判定に戻り、内部施設を編集できる。
- 組み合わせ後も内部施設の生産と上位建物の生産を両方行う。

「ゲーム内の資源」と「現実由来のエネルギー」は区別する。工場がガス・電気・水そのものを再生産できるかは、まだ確定していない。ペンギンは施設に配属せず、所持しているだけで資源の獲得量へ効果を与える方針とする。19種の対象資源と加算・乗算の数値案は[ペンギンの種類と効果](penguin-effects-proposal.md)を参照する。具体的な割合と同種の重なり方は検討案。

ズーム段階の定義、表示・当たり判定、MVPの解放範囲、受け入れ条件は[ランクとズームアウトの仕様](zoom-out.md)にまとめる。

### ランク上げ用の納品とペンギンの獲得

生産した品物はランク上げのために納品する。MVPではすり身・干物を合計5個納品するごとにランクを1つ上げ、ランク2で3ズームを解放する。製品版の品目別評価とランクごとの必要量は未決。週単位の納品量ノルマと、その超過分に応じた報酬は採用しない。

ペンギンは「種類の解放」と「個体の獲得」を分ける。種類を解放すると、その種類をすれ違いで獲得できるようになる。種類の解放だけでは個体を獲得しない。

種類の解放条件は未決。週ノルマの超過報酬による特殊資源の獲得経路は取り下げる。特殊資源を別の方法で得て解放に使うかどうかも、現時点では決めていない。

納品によってランクを上げ、ズーム段階を解放する方針は確定。納品先を城にすることや、城の成長とランクの関係、土地の拡張の具体的な条件は引き続き検討する。

### 土地の拡張

1回の拡張で2×2マス、計4マスを追加する。拡張費用、初期の土地の広さ、城レベルによる拡張上限は未決。

拡張区画と組み合わせ区画の境目をそろえる案を推奨する。1区画を広げると1組分の建物を配置でき、土地を広げる操作と組み合わせの関係を理解しやすい。ただし、固定の区画で組み合わせる方式自体はまだ提案であり、今回の拡張単位の決定と分けて扱う。

2×2が最下層のマスを指すか、表示中の階層のマスを指すかは未決。後者では上位階層からの拡張ほど下位の土地を多く追加することになるため、拡張する階層を決めてから費用と上限を設計する。既存の土地に接する区画だけを開けるか、離れた土地も開けるかも未決。

### 隣接する施設と倉庫の物流

施設の配置で資源の通り道を作り、倉庫で物流を操作する。ここでいう接続は、線を描く操作を前提にしない。横並び以外に上下や斜めもつながるか、倉庫同士が離れていてもつながるかは未決。

倉庫は、必要な資源を必要な施設へ送るための調整を自動で行う。以前の提案にあった、送り先・優先順位・確保量を利用者が細かく指定する方式は基本にしない。利用者は施設や倉庫を配置し、配送の結果を見て配置を改善する方向で検討する。

| 未決の論点 | 確かめること |
|---|---|
| 停止中の中継 | 自分が使わない資源も中継できることは確定。生産停止中も中継するかは未決 |
| 在庫と移動 | つながった範囲で在庫を即時共有するか、施設ごとに持ち、隣へ順番に渡すか |
| 輸送の制約 | 移動時間・運搬量・保管量に上限を設けるか。送り先が満杯ならどこで止めるか |
| 自動配分 | 同じ資源を複数の施設が必要としたとき、どの施設へ渡すか。倉庫が調整する範囲と基準 |
| 組み合わせの境目 | 上位資源は下位で消費しない。外部とのやり取りが内部4棟のどの位置につながるか、上位資源をどの経路で中継するか |

つながった範囲の在庫を即時共有する方式では、途中の配置や倉庫による振り分けが生産にどれだけ影響するかを確かめる。施設ごとに受け渡す方式では、資源が往復し続けないこと、複数の送り先への配分が分かること、停止理由が見えることを検証する。方式はまだ確定しない。

上段2棟・下段3棟などの不規則な配置、2×2の区切り方、倉庫4棟から大型倉庫になる案は、[組み合わせと倉庫の提案](logistics-proposal.md)にまとめる。固定区画・輸送能力・大型倉庫の効果はいずれも検討案であり、確定した仕様ではない。

## 組み合わせの理解図

以下は、直前の段階の2×2を上位の1グリッドとして扱う図。すべてのズーム段階でこの規則を繰り返すため、3ズームの1グリッドは1ズームの4×4に相当する。4棟の種類・並び順・向き・接続の成立条件は未決で、図のA〜DとXは説明用の記号。各段階の上位施設の成立条件は別途決める。

```text
細かい段階                   1段階ズームアウト
┌────┬────┐                 ┌─────────┐
│ A棟│ B棟│ ─────────────→  │ 組み合わせX │
├────┼────┤                 └─────────┘
│ C棟│ D棟│ ←─────────────  元の4棟へ戻して編集
└────┴────┘

内部: A〜Dの生産が継続
上位: Xとして別の資源も生産
```

確定しているのは「両方の生産がある」まで。上位の生産が内部の成果物を材料にするのか、組み合わせの追加報酬なのかは未決。カメラを往復するだけで生産が増えることや、表示されない建物の消費が消えることを防ぐため、表示段階と生産状態の関係を先に決める。

### 上位建物の生産案

検討では、資源の使い分けと、4棟の組み合わせを工夫する面白さを両方残す。内部の資源を上位建物がすべて使う方式では、ほかの使い道を選びにくい。また、どんな4棟でも同じように生産できる方式では、組み合わせを考える意味が薄れる。生産方式は引き続き未決とする。

| 案 | 生産の関係 | 考えられる遊びと課題 |
|---|---|---|
| 内部の資源を全量変換する | 内部の出力を上位建物でまとめて別の資源に変える | 仕組みは分かりやすいが、資源をほかの工場へ回す余地が少ない |
| 構成に応じたレシピで必要量だけ使う（推奨案） | 4棟の構成で上位建物の種類・候補レシピを決め、指定された資源だけを必要量消費する | 構成、生産量の比率、資源の送り先を工夫できる。内部・上位・外部での消費の優先順位は設計が必要 |
| 構成に応じて追加生産する | 4棟の構成で上位建物を決め、内部の成果物は使わず、上位用のエネルギーで別の資源を作る | 内部の出力を保ちやすいが、置くだけで報酬を得る遊びに偏らないか検証が必要 |

推奨案では、まず4棟の構成が何を生産できるかを決める。そのうえで内部接続と資源の配分を工夫し、上位のレシピを動かす。どの構成を成立とするか、並び順や向きも条件にするかは未決。

説明用の例として、内部が毎分Aを4個、Bを2個生産し、上位のレシピがAを2個、Bを1個使ってCを1個作る場合を考える。上位で使わなかったAを2個、Bを1個は、保管や外部への輸送に回せる。この数量は確定値ではなく、各工場のエネルギー消費も別途必要になる。

内部生産を優先して余りだけ上位へ渡すか、上位用に一定量を取り分けるか、外部出荷を優先するかは未決。倉庫がこの配分を自動で調整する案を検討する。上位の資源を下位施設が消費することは想定せず、中継と材料の消費を区別する。

最初の体験の提案は、資源を受け取る→工場を建てる→加工型を隣に置く→倉庫を置いて自動配送を確認する→4マスの組み合わせを見つける→ズームアウトして新しい生産を確認→再展開して改善、の順。続いて納品でランクを上げ、3ズームの解放を目指す。MVPでは2次資源5個の納品を仮条件とする。

## スマホでの操作と性能

組み合わせによって、広い工場を少数の建物として把握・操作できることが狙い。内部4棟のモデルやアニメーションを上位の表示に置き換えられれば、描画に関わる CPU・GPU の負荷を減らせる可能性がある。

ただし、内部と上位の生産を両方行うため、**描画を減らすだけでは生産計算の CPU 負荷は減らない**。計算の集約・更新頻度・非表示オブジェクトの停止は別途設計する。性能改善は未計測であり、達成済みとは扱わない。

試作では同じ工場構成・経過時間で、詳細表示と集約表示のフレーム時間、描画 CPU/GPU 時間、生産計算時間、メモリ、Draw Call を比較する。ズームの反復で資源総量・在庫・生産進行が意図せず変わらないことも確かめる。対象 iPhone、施設数、目標 FPS は未決。

## 次に設計する範囲

組み合わせのレシピや成立条件の詳細は、後で検討する。これまでの[生産案の比較](#上位建物の生産案)と[物流の提案](logistics-proposal.md)は検討資料として残し、採用した仕様とは扱わない。

直近では、次の順に設計を進める案とする。

1. ランク上げと3ズーム解放に必要な納品の品目・数量・評価方法を決める。同じ納品を重複して数えない処理も設計する。
2. ペンギンの種類を解放する条件と、解放済みの種類をすれ違いで獲得するルールを決める。ペンギンのゲーム内での働きも整理する。
3. 城の成長条件、2×2の土地拡張の対象階層・費用・上限、資源不足からの復帰方法を決める。
4. iOS実機で現実連携の条件を検証する。[既存コードと調査](research.md)の制約を踏まえ、実装可能な条件と代替案を確定する。
5. 組み合わせの詳細を決めた後、配置・自動配送・生産・納品・拡張を通して試作し、[ペルソナ仮説](personas.md)を用いて操作性と継続動機を検証する。

残りの未決事項は[質問一覧](questions.md)で管理する。数値は試作評価で調整し、未決の値を確定値として実装へ持ち込まない。

この段階ではコード・API・従来の決定事項を書き換えない。通信を追加・変更する際は、本リポジトリの規則どおり `api/openapi.yaml` と `api/examples/` を先に更新する。実装時に新たな衝突が見つかったら、勝手に旧仕様へ合わせず、具体的な差と選択肢を確認する。
